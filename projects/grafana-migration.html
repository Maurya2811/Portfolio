Grafana Dashboard Migration Tool

A Python tool that moves monitoring dashboards between environments. A manual, error-prone 8-hour job became a 20-minute run with a reviewable diff.

Simplified reference architecture written from memory for discussion. Client identity, service names, topology, configuration and code are deliberately omitted or generalised.

RoleSole author
Scale200+ dashboards · 3 environments
Time8 hrs → 20 min (−95%)
PropertyIdempotent, dry-run first

Problem

  • Dashboards were built in one environment and had to be recreated in others that sit on separate networks, each with its own datasource names and folder layout.
  • Doing it by hand meant export, edit JSON, import, and fix broken panels. It took about 8 hours per migration, and mismatched datasource references often went unnoticed until someone needed the panel.

Design

  • Export dashboards and folders from the source through the Grafana HTTP API.
  • Transform each dashboard JSON using a per-environment config file: datasource name/UID mapping, folder mapping, and stripping of instance-specific fields (id, version).
  • Dry-run by default: print a diff report of what would be created, changed or left alone, plus any datasource reference with no mapping.
  • Import with overwrite keyed on dashboard UID, so re-running is safe and the target converges to the source.
  • Credentials come from environment variables, never from the config file or the repo.

Reference architecture

flowchart LR
  SRC["Source Grafana"] -->|HTTP API export| EXP["Exporter"]
  CFG["env config: datasource + folder maps"] --> TR["Transformer"]
  EXP --> TR
  TR --> VAL{"All references mapped?"}
  VAL -- no --> REP["Diff report + unmapped list"]
  VAL -- yes --> DRY{"--apply?"}
  DRY -- no --> REP
  DRY -- yes --> IMP["Importer: overwrite by UID"]
  IMP --> TGT["Target Grafana (env 1..3)"]
  IMP --> REP

Trade-offs

DecisionChoseOverWhy
Identity of a dashboardUID-keyed overwriteCreate-new on each runIdempotent re-runs, no duplicates
Environment differencesDeclarative config fileHard-coded rewritesA new environment is a config entry, not a code change
Default modeDry-runApplyReviewers see the diff before anything changes

Failure modes I designed for

  • Unmapped datasource: the run fails before import and lists every offending panel.
  • Partial failure mid-import: it is safe to re-run because imports are idempotent.
  • Missing folder in the target: the folder is created from the mapping before any dashboards are imported.

Impact

  • Migration time 8 hrs → 20 min (−95%).
  • 200+ dashboards moved across 3 network environments.
  • Broken-panel surprises after migration disappeared, because unmapped references fail early.

What I would do differently

  • Keep dashboards as code in Git and provision them, so migration is just a deploy.
  • Add a CI job that validates every dashboard JSON against each environment's mapping.
