Robotic Shuttle Integration & Telemetry

Integrated a third-party fleet of robotic shuttles and lifts into an existing ASRS platform for a US healthcare logistics provider, and built the telemetry pipeline and health dashboards operators now use to find and fix hardware problems.

Simplified reference architecture written from memory for discussion. Client identity, hardware vendor, service names, protocols' message formats, configuration and code are deliberately omitted or generalised.

RoleSoftware Development Engineer
Scale50+ shuttles and lifts
Capture99.6% of telemetry events
Impact-70% downtime diagnosis time

Context

The site already ran our ASRS software for storage and retrieval. The client added a fleet of robotic shuttles and lifts from a third-party vendor. That hardware had its own controller, its own state and its own interfaces (TCP and REST), and it had to behave as part of one system from the operator's point of view.

Problem

  • Two stacks with different protocols and two copies of the truth about where a shuttle was and what it was doing.
  • No single view of fleet health. When a shuttle stalled, a hand-off failed or a lift timed out, engineers pieced the story together from separate logs.
  • Diagnosis took long enough to hurt throughput on a site with strict service levels.

What I did

  • Built the hardware adapter. A Spring Boot service that speaks the vendor's TCP and REST interfaces on one side and our internal command and event contracts on the other. The rest of the platform never sees vendor-specific formats (an anti-corruption layer).
  • Built the telemetry pipeline. The adapter publishes status and fault events to RabbitMQ. An ingestor consumes them and upserts the current state per device into MongoDB, plus an append-only history for trend queries. It covers 50+ devices at 99.6% capture.
  • Made consumption safe to retry. Consumers are idempotent (dedupe on message id and ignore out-of-order state). Messages that keep failing go to a dead-letter queue and can be replayed.
  • Built health dashboards in Grafana showing connectivity, fault state, queue depth and stale devices, which cut downtime diagnosis time by 70%.

Reference architecture

flowchart LR
  SH["Robotic shuttles (50+)"] -->|TCP / REST| ADP["Hardware Adapter"]
  LF["Lifts"] -->|TCP / REST| ADP
  ADP -->|commands| SH
  ADP <--> MQ[("RabbitMQ")]
  MQ --> CORE["ASRS Core Services"]
  CORE --> SQL[("MySQL")]
  MQ --> ING["Telemetry Ingestor"]
  ING --> CUR[("MongoDB: current state")]
  ING --> HIST[("MongoDB: event history")]
  MQ -. failed .-> DLQ[("Dead-letter queue")]
  DLQ -. replay .-> ING
  CUR --> DASH["Grafana health dashboards"]
  HIST --> DASH

Design principle: vendor protocols stop at the adapter. Inside the platform, every device is described by the same small set of commands and events, so a second vendor would need a new adapter and nothing else.

Trade-offs

DecisionChoseOverWhy
Vendor integrationDedicated adapter serviceCalling vendor APIs from core servicesKeeps vendor formats and failure modes out of the core; one place to change if the vendor API changes
Telemetry storeMongoDB (current state + history)The transactional SQL databaseDevice payloads vary by type; high write volume would compete with order transactions
Delivery semanticsAt-least-once with idempotent consumersTrying for exactly-onceSimpler and reliable with RabbitMQ; duplicates are cheap to detect
Failed messagesDLQ with replayInfinite retry or dropInfinite retry blocks the queue; dropping loses data an engineer may need for diagnosis

Failure modes I designed for

  • Device goes silent: a stale-heartbeat check flags it on the dashboard instead of showing its last good state.
  • Broker redelivery or failover: idempotent upserts mean redelivered events don't corrupt state.
  • Out-of-order messages: events older than the stored state are ignored for current state but kept in history.
  • Vendor API errors: the adapter translates them into fault events with a reason, so they're visible rather than swallowed.

Impact

  • 50+ third-party shuttles and lifts working as part of the ASRS platform.
  • 99.6% telemetry capture rate.
  • Downtime diagnosis time -70%.

What I would do differently

  • Use a purpose-built time-series collection or store for history from the start, with a retention policy.
  • Define the internal device contract as a versioned schema up front, so adding fields doesn't need coordinated releases.
