Cross-Service Observability: Root-Cause Analysis in One Query

The design behind the retail DC platform throughput work. Every service reports irregular events in one shared shape to a dedicated store. Root-cause analysis went from grepping pod logs to a single correlated query.

Simplified reference architecture written from memory for discussion. Client identity, service names, topology, configuration and code are deliberately omitted or generalised.

RoleDesigner and implementer
PatternAsync event envelope + read-side store
StoreMongoDB, TTL retention
OutcomeEvidence base for +50% throughput

Problem

  • A tote passes through several services (allocation, station, robot cell, pack) before it leaves the floor. Each service logged problems in its own format, in its own pods.
  • When a tote got stuck, nobody could answer the basic questions quickly: where did it wait, for how long, and why?
  • Kubernetes log retention is short, so the evidence from a bad shift was often gone by the time anyone looked.

The event envelope

Every service emits the same small document whenever something deviates from the happy path, and at each stage boundary. Keeping the envelope uniform is what makes cross-service queries possible. 

{
  "eventId":       "uuid",
  "correlationId": "order-or-tote-lifecycle-id",
  "entityId":      "tote-id",
  "sourceService": "station-service",
  "stage":         "AT_STATION",
  "reasonCode":    "PICK_TIMEOUT",
  "severity":      "WARN",
  "stageEnteredAt": "2026-03-02T10:14:07Z",
  "ts":            "2026-03-02T10:16:41Z",
  "attributes":    { "station": "S-03" }
}

reasonCode comes from a shared enum, not free text, so it can be grouped and ranked. attributes is the escape hatch for service-specific detail.

Reference architecture

flowchart LR
  subgraph SVC["Business services"]
    A["Allocation"]
    S["Station Service"]
    R["Robot Cell Adapter"]
    P["Pack Station"]
  end
  SVC -->|async publish| X[("Topic exchange: irregular.#")]
  X --> Q["Dedicated queue"]
  Q --> C["Irregular-Event Consumer"]
  C -->|bulk insert| M[("MongoDB: irregular_events")]
  C -. poison .-> DLQ["Dead-letter queue"]
  M --> G["Grafana panels"]
  M --> RCA["Ad-hoc RCA queries"]
  • Publish: a thin shared library builds the envelope and publishes it asynchronously to a topic exchange, with routing keys like irregular.station.pick_timeout. If publishing fails, it logs and moves on; it never throws into business code.
  • Consume: one consumer service batches inserts into MongoDB. It writes with eventId as _id, so redelivered messages are harmless duplicates.
  • Indexes: compound index {correlationId: 1, ts: 1} for lifecycle queries, {reasonCode: 1, ts: -1} for ranking, and a TTL index on ts for automatic retention.

Queries that answer real questions

  • "What happened to this tote?" Find by correlationId sorted by ts, which gives the full cross-service timeline.
  • "Where do totes wait?" An aggregation that filters a time window, computes ts - stageEnteredAt per event, groups by stage and returns count, average and p95 dwell. This one query showed that stations were being starved, not that they were slow.
  • "What breaks most?" Group by reasonCode over the last shift, sorted by count.

Grafana panels sit on the same queries: stuck totes (no stage change for N minutes), top reason codes per shift, and dwell time by stage.

Trade-offs

DecisionChoseOverWhy
Delivery guaranteeBest-effort async publishTransactional outboxDiagnostics must never slow or block the order path. A lost diagnostic event is acceptable here
StoreMongoDB collectionExtra tables in the transactional SQL DBNo load on the hot path, flexible attributes, built-in TTL
Event shapeOne shared envelope plus enum reason codesPer-service log formatsCross-service grouping only works if every producer uses the same fields
RetentionTTL indexManual archival jobsNothing to operate; a fixed window covers RCA and trend needs

Failure modes I designed for

  • Broker unavailable: the publisher drops the event and logs locally, so business flow continues.
  • Consumer behind or down: events queue on the broker under a length limit, and the consumer catches up with batch inserts.
  • Duplicates: eventId as _id makes inserts idempotent.
  • Malformed events: they are rejected to a DLQ instead of blocking the queue.

Impact

  • Root-cause analysis went from grepping logs across several pods to one correlated query.
  • Stage-level dwell time was the evidence base for the allocation fixes that took picking from 800 → 1,200 totes/hr (+50%).
  • Shift reviews now start from a ranked reason-code list instead of anecdotes.

What I would do differently

  • Carry OpenTelemetry trace context in the envelope, so an irregular event links straight to its trace.
  • Version the envelope schema explicitly from the first release.
