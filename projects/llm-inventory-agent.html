LLM Agent (RAG + Tool Calling) That Cut Support Tickets 40%

A conversational assistant that answers warehouse operators' inventory questions ("where is SKU X?", "why is this order not released?") from live data and product documentation. It resolved 75%+ of queries without a human and cut support tickets by 40%.

Simplified reference architecture written from memory for discussion. Client identity, service names, topology, configuration and code are deliberately omitted or generalised.

RoleDesigner and implementer
PatternRAG + allowlisted tool calls
Auto-resolved75%+ of queries
Support load−40% tickets

Problem

  • Operators and site supervisors raised support tickets for questions the system could already answer: stock location, order status, why a task was blocked.
  • Answering them meant a support engineer running queries by hand or looking things up in SOPs. It was slow for the operator and repetitive for the team.

Design

  • Two knowledge sources: retrieval over product docs and SOPs for "how / why" questions, and tool calls into live inventory data for "what / where" questions.
  • Tools, not SQL: the model never writes SQL. It picks one tool from an allowlist (e.g. getStockBySku, getOrderStatus, getLocationContents) and fills typed parameters. Each tool is a parameterised, read-only query behind a service API.
  • Grounded answers: the final answer must cite what it is based on (the tool result or the document passage). If neither supports an answer, the assistant says so and hands off.

Guardrails

  • Read-only by construction: a read-only database user and no write tools at all. A prompt can't talk its way into a mutation.
  • Allowlist + schema validation: an unknown tool or invalid parameter is rejected before anything executes.
  • Row limits and timeouts on every tool, so one question can't load the database.
  • No personal data in tool outputs or prompts; inventory and order-state fields only.
  • Fallback to a human: low confidence, no grounding, or a rejected tool call creates a ticket with the conversation attached.

Trade-offs

DecisionChoseOverWhy
Data accessAllowlisted, parameterised toolsText-to-SQLPredictable, reviewable queries; no injection or runaway scans against production
KnowledgeRetrieval over docsFine-tuningDocs change often; retrieval updates instantly and can cite its source
Failure behaviourRefuse and hand offBest-guess answersA wrong stock answer on the floor costs more than a ticket

Impact

  • 75%+ of operator inventory queries resolved without a human.
  • −40% support ticket volume.

How I'd evaluate it today

  • A versioned golden set of real (anonymised) operator questions with expected tool calls and answers, run in CI on every prompt or tool change.
  • Separate scores for tool selection, parameter correctness and answer faithfulness to the tool output, so a regression points at the failing layer.
  • Production telemetry: hand-off rate, rejected tool calls, and thumbs-down by question type.
  • Adversarial cases: prompt-injection attempts in SKU fields, requests for write actions, out-of-scope questions.

What I would do differently

  • Build the golden-set evaluation before the first release, not after.
  • Log structured traces (prompt, tool call, result size, latency) from day one to make tuning data-driven.
