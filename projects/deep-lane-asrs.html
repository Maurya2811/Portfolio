Robot Orchestration for High-Density Automated Storage

Backend control for a high-density automated storage and retrieval system at a tyre manufacturing plant in India: pallets stored five deep across nine levels, moved by third-party cranes, shuttles, duplex lifts and conveyors, all orchestrated by a Java Warehouse Control System (WCS).

Simplified reference architecture written from memory for discussion. Client identity, hardware vendors, service names, slotting parameters, configuration and code are deliberately omitted or generalised.

RoleSoftware Development Engineer
Scale500+ daily transactions
Interface testing3 months → 3 weeks
UAT~2x faster (6+ wks → 3 wks)

Context

Deep-lane storage packs more pallets into the same footprint by placing them one behind another, here up to five deep on each of nine levels. A crane or lift brings a shuttle to the right level and lane, and the shuttle travels into the lane to store or fetch a pallet. The hardware came from third-party vendors; our WCS had to coordinate all of it and keep inventory exact.

Problem

  • Deep lanes block access. Getting a pallet at the back of a lane means first relocating the pallets in front of it, so a bad put-away decision costs extra moves later.
  • Many hardware interfaces. Cranes, shuttles, duplex lifts and conveyors each had their own controller and interface, and every hand-off between them had to be exact.
  • Tight timeline. Interface development and testing with the client was on track to take about three months.

What I did

  • Built WCS orchestration in Java / Spring Boot for put-away and retrieval: breaking each task into crane, lift, shuttle and conveyor steps, sending commands over the message bus, and committing inventory only after the hardware confirms.
  • Implemented scored slot selection. For each put-away, candidate slots are scored on FIFO order, SKU affinity (same SKU in the same lane) and expected re-handling cost, and the best candidate wins. This keeps rear-of-lane retrievals rare.
  • Handled blocked retrievals. When the target pallet is behind others, the WCS plans relocation moves for the front pallets first, then the retrieval, and updates inventory at each step.
  • Unblocked the QA and Process teams by helping finish interface development and testing. Client interface testing went from 3 months to 3 weeks and the UAT cycle from 6+ weeks to 3 weeks. I resolved 20+ UAT defects along the way.

Why 5-deep is hard: storage density and access cost pull in opposite directions. Each put-away decision changes how many relocation moves a future retrieval will need, so slot selection has to look ahead, not just find an empty slot.

Trade-offs

DecisionChoseOverWhy
Slot choiceScore a candidate setFirst free slotFirst-free is fast but causes many relocations later; scoring trades a little compute for far fewer moves
Inventory commitAfter hardware confirms each stepOptimistic commit on commandHardware can fail mid-move; inventory must match what's physically in the lane
Hardware integrationOne adapter per device type over the busOrchestrator calling controllers directlyIsolates vendor interfaces and lets devices fail independently
RelocationPlan all blocking moves before startingDecide move by moveA full plan can be checked for free capacity first, so a retrieval never stalls half-done

Failure modes I designed for

  • Hardware fault mid-task: the task stops at the last confirmed step, inventory stays correct, and the task can be resumed or reversed.
  • Duplicate or late confirmations: step confirmations are idempotent, so a repeated message does not move inventory twice.
  • No free relocation slot: detected at planning time, and the retrieval is queued instead of started.

Impact

  • Production ASRS handling 500+ daily transactions.
  • Client interface testing 3 months → 3 weeks.
  • UAT cycle about 2x faster (6+ weeks → 3 weeks); 20+ UAT defects resolved.

What I would do differently

  • Build hardware simulators for each device type early, so interface testing doesn't depend on site access.
  • Write the task state machine down as an explicit model from the start, which makes resume and reverse logic easier to test.
