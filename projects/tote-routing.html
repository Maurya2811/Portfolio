Tote Routing Optimisation

Redesigned how totes are routed from storage to goods-to-person pick stations in a D2C retailer's fulfilment centre in India. I modelled the transport network as a graph with live congestion weights, which cut travel time by 15% and lifted pilot throughput by 12%.

Simplified reference architecture written from memory for discussion. Client identity, site layout, service names, parameters, configuration and code are deliberately omitted or generalised.

RoleSoftware Development Engineer
Travel time-15%

Throughput+12% in pilot

Context

Totes leave automated storage and travel over a network of conveyors, junctions and diverts to goods-to-person stations, where operators pick items. If totes arrive late or bunch up, pickers wait and the whole site slows down.

Problem

  • The existing router used fixed rules: the same path for a given source and destination, whatever the load.
  • At peak, some segments congested while alternatives sat idle. Totes queued, stations starved and end-to-end latency grew.
  • Route resolution was slow enough to add noticeable delay to each routing decision.

What I did

  • Modelled the network as a weighted directed graph. Nodes are junctions and diverts; edges are conveyor segments. Each edge's weight is its base travel time plus a congestion penalty.
  • Fed live congestion into the weights. Conveyor telemetry updates the congestion penalty on each edge, so routes reflect current load rather than a static map.
  • Implemented Dijkstra for the primary route and Yen's K-shortest paths (k=2) to precompute an alternate. When the primary path crosses a congestion threshold, the router switches to the alternate without re-planning on the hot path.
  • Optimised the data structures (adjacency lists, a binary-heap priority queue, cached graph snapshots) to cut path resolution time.
  • Benchmarked on replayed traces from production before the pilot, comparing the new router against the old one on the same tote sequences.

Reference architecture

flowchart LR
  STORE["Storage exit"] -->|tote ready| ROUT["Tote Router Service"]
  TELE["Conveyor telemetry"] -->|segment load| WGT["Edge-weight updater"]
  WGT --> SNAP[("Graph snapshot: edges + live weights")]
  SNAP --> ROUT
  ROUT -->|route assigned| MQ[("RabbitMQ")]
  MQ --> CTRL["Conveyor Controller"]
  CTRL --> NET["Conveyor network"]
  NET --> GTP["GTP pick stations"]
  ROUT --> MET["Grafana: travel time, reroutes"]

Complexity: Dijkstra with a binary heap runs in O((V + E) log V) per query, which is small for a conveyor network. Yen's K-shortest with k=2 costs roughly k·V extra Dijkstra runs, so it's computed ahead of time and refreshed when weights change. Switching to the alternate at decision time is then O(1).

Low-level flow — route planning

flowchart TB
  A["Tote ready: source, destination"] --> B["Read latest graph snapshot"]
  B --> C["Primary path via Dijkstra"]
  C --> D{"Primary over congestion threshold?"}
  D -- no --> F["Commit primary path"]
  D -- yes --> E["Use precomputed alternate (Yen, k=2)"]
  E --> F
  F --> G["Publish route.assigned"]
  G --> H["Record travel time for metrics"]

Trade-offs

Number of alternatesk = 2Larger kMost of the gain came from one alternate; more paths cost more compute and rarely got chosen

Failure modes I designed for

  • Telemetry stops: weights fall back to base travel times, so routing degrades to the static behaviour instead of failing.
  • Both paths congested: the router commits the cheaper of the two rather than waiting, so totes keep moving.
  • Oscillation: a threshold with hysteresis stops totes flipping between paths when congestion hovers near the limit.

Impact

  • Tote travel and path resolution time -15%.
  • -200 ms latency per routing decision.
  • Warehouse throughput +12% during the pilot.

What I would do differently

  • Build a small simulator early so routing policies can be compared without waiting for trace replays.
  • Expose congestion weights and route choices as first-class metrics from day one, not after the pilot.

  2. How Yen's algorithm works and why precomputing alternates keeps decisions O(1).
  3. Hysteresis to avoid route flapping under fluctuating load.
  4. How replayed traces made the before/after comparison fair.
