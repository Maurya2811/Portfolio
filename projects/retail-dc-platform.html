+50% Throughput on a 24/7 Platform of 20+ Java Microservices

Forward-deployed on a live, 3PL-operated distribution centre for a tier-1 global retail brand. I own feature delivery and production health across a 20+ microservice Warehouse Execution System, and I led the throughput work that took goods-to-person picking from 800 to 1,200 totes/hr.

Context

A Warehouse Execution System (WES) sits between the client's host WMS/ERP and the automation hardware: robotic storage, goods-to-person (GTP) pick stations, robot cells, conveyors and pack stations. Each capability is its own Spring Boot service, and they talk through a message broker. The site had a contracted throughput SLA, and a commercial milestone depended on meeting it.

Problem

  • Pick stations averaged about 800 totes/hr, well short of the contracted rate.
  • Every team blamed a different layer: hardware, the network, the WMS or "the software". Nobody had a cross-service view of where a tote actually spent its time.
  • Irregular events (stuck totes, failed hand-offs, hardware timeouts) showed up only in per-service logs, so root-cause analysis meant grepping several pods by hand.

What I did

  • Built an irregular-event store. Services publish a small, uniform IrregularEvent (correlation id, tote/order id, stage, reason, timestamps) to the broker, and a consumer persists them to a MongoDB collection indexed by correlation id and time. One query now shows a tote's whole lifecycle across services. (Design deep-dive.)
  • Measured before changing anything. From the event data I built stage-by-stage dwell-time breakdowns. These showed the bottleneck was in software: work was released to stations in an order that starved some stations and queued others, and mixed business flows contended for the same automation.
  • Fixed the release and allocation logic. Changed how work is allocated and released to stations, and segregated business flows (e.g. replenishment vs. customer orders) so they stopped competing for the same resources. This gave +30% operational efficiency for the client.
  • Delivered change requests end-to-end across the stack: design, implementation, Helm-based rollout, on-site validation with operations, and hypercare.

Design principle: each service owns its own data and contract, and side-effects cross service boundaries only as events. The irregular-event store is a read-side copy built for diagnosis, so it never sits on the transactional hot path.

Trade-offs

DecisionChoseOverWhy
Where diagnostics liveSeparate MongoDB event storeQuerying transactional SQL tablesKeeps load off the hot path; the schema-flexible documents suit heterogeneous event payloads
How events are emittedAsync publish, fire-and-forgetSynchronous write inside the business transactionA diagnostics outage must never stop the floor; losing a diagnostic event is acceptable, losing an order is not
How to raise throughputFix release / allocation policy firstScaling pods or adding hardwareThe data showed starvation and contention, not lack of compute; scaling would have hidden the problem
How to roll outFeature-flagged, shift-by-shiftBig-bang releaseThe site is live 24/7, and operations needed a fast rollback path

Failure modes I designed for

  • Broker redelivery: consumers are idempotent (dedupe on message id plus state check), so redelivered events don't double-apply.
  • Poison messages: bounded retries, then a dead-letter queue with replay tooling.
  • Hardware timeouts: they raise an irregular event with a reason code instead of failing silently, so they show up in the stuck-tote dashboard.

Impact

  • GTP picking throughput 800 → 1,200 totes/hr (+50%).
  • Closed the gap to the contracted throughput SLA, which unblocked a seven-figure (AUD) contractual milestone.
  • +30% client operational efficiency from segregating business flows.
  • Root-cause analysis went from grepping pods to a single correlated query.

What I would do differently

  • Adopt OpenTelemetry trace context in every event from day one, so dwell-time analysis and tracing share one correlation id.
  • Use the transactional outbox pattern for business-critical events, so publish and DB commit are atomic.

// interview talking points

  1. How I proved the bottleneck was in software, not hardware: dwell-time per stage from correlated events.
  2. Why diagnostics are async and lossy-tolerant while business events are not.
  3. How to change allocation logic safely on a live 24/7 site: flags, shadow comparison, shift-based rollout.
  4. Idempotency and DLQ design for at-least-once delivery.
