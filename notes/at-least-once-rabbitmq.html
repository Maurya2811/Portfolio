At-least-once delivery on RabbitMQ: idempotent consumers, DLQ and replay

Teams new to message brokers often ask for "exactly-once delivery". On RabbitMQ, as on most brokers, you don't get that across a network boundary. What you can build is at-least-once delivery plus idempotent processing, which gives you exactly-once effects. That is what the business actually cares about. Three pieces make it work: manual acknowledgements, idempotent consumers, and a dead-letter path you can replay from.

1. Acknowledge after the work, not before

With auto-ack, the broker forgets a message as soon as it is handed to the consumer. If the pod dies halfway through processing, the message is gone. Use manual acknowledgement and ack only after the database transaction commits. If the consumer crashes before the ack, the broker redelivers. That redelivery is the "at least" in at-least-once. 

@RabbitListener(queues = "order.released", ackMode = "MANUAL")
void onReleased(Message msg, Channel ch) throws IOException {
    long tag = msg.getMessageProperties().getDeliveryTag();
    try {
        handler.process(parse(msg));     // commits its own transaction
        ch.basicAck(tag, false);
    } catch (TransientException e) {
        ch.basicNack(tag, false, true);  // requeue, try again
    } catch (Exception e) {
        ch.basicNack(tag, false, false); // reject -> dead-letter exchange
    }
}

On the producer side, publisher confirms tell you the broker accepted the message. Without them a publish can be lost silently during a broker failover.

2. Make the consumer idempotent

Redelivery means the same message can arrive twice: after a crash, after a network blip between commit and ack, or after a replay. The consumer has to make the second delivery a no-op. Two techniques cover almost every case:

  • Dedupe table. Every message carries a unique messageId. Insert it into a processed_messages table in the same transaction as the business change. A unique-key violation means "already done": ack and move on.
  • State-machine guard. Apply the change only if the entity is in the expected prior state, e.g. UPDATE task SET state='PICKED' WHERE id=? AND state='AT_STATION'. Zero rows updated means the event was already applied, or it is stale.
@Transactional
void process(TaskEvent e) {
    if (!dedupe.tryInsert(e.messageId())) return;        // seen before
    int rows = tasks.transition(e.taskId(), AT_STATION, PICKED);
    if (rows == 0) log.info("stale or duplicate {}", e); // safe no-op
}

The state guard also protects against out-of-order delivery. RabbitMQ preserves order per queue, but not once retries, multiple consumers or several producers are involved.

3. Dead-letter, don't loop

A poison message (bad payload, a bug, a missing reference) that is requeued forever will spin the consumer at 100% CPU and block everything behind it. Configure the queue with a dead-letter exchange: 

x-dead-letter-exchange    = dlx
x-dead-letter-routing-key = order.released.dlq

Transient failures (database briefly unavailable) should retry with a bounded count and some delay. A common approach is a retry queue with a per-message TTL that dead-letters back to the main queue, with the attempt count kept in a header. Permanent failures, or anything over the retry budget, go to the DLQ.

4. Replay is a feature

A DLQ that nobody drains is a slow data-loss bug. Treat replay as a first-class tool:

  • Alert on DLQ depth > 0, and show it on the same dashboard as consumer lag.
  • Keep the original headers and add the failure reason when dead-lettering, so triage doesn't need log archaeology.
  • Provide a replay command that moves selected messages back to the main exchange after the fix ships. Because consumers are idempotent, replaying something that was half-applied is safe.

What this buys you

With these pieces, a broker restart, a pod eviction or a bad deploy is an operational event, not a data incident. Messages are either processed once in effect, waiting in a queue, or parked in a DLQ with a reason attached. Nothing disappears.

Where a business event has to be published reliably together with a database change, add the transactional outbox. Write the event to an outbox table in the same transaction, and have a relay publish it. That closes the remaining gap: a crash between commit and publish.
